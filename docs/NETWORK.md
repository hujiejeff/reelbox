# 网络出口与系统代理

**应用里没有「设置代理」这个开关。** 出口一律跟着系统走:系统开着代理就走代理,系统没开
就直连。普通用户不需要知道这件事,也不该被问 —— 所以设置页里没有这一栏,连不上时的
错误卡片只给「重试」和「源管理」。

更进一步:出口不是全局定一次的,而是**按域名自动选路并记下来**(见「按域名自动选路」)。
同一个应用里,访问采集站和访问国内 CDN 需要的是**相反**的那条路,所以只能按 host 收敛。

状态:已实现,`cargo test -p reelbox-core` 覆盖解析链、FakeIP 例外、按域名的候选顺序,
以及"学过命中 / TTL 过期 / 容量淘汰 / 两条路都失败时的错误串 / 只在成功后记忆"。

## 为什么"开了系统代理还是连不上"(历史)

应用里有两条完全独立的网络路径:

| 谁在发请求 | 实现 | 跟系统代理 |
| --- | --- | --- |
| 播放器拉分片、页面里的 `<img>` | WebView2(Chromium) | 是,内核自己读系统设置 |
| 源接口、详情、取流、封面、插件里的 `http.get` | Rust + reqwest | **否**,要自己解析 |

WebView2 是 Chromium,系统代理它自己会跟;reqwest 不会。所以代理开着、分片能拉,列表却
超时 —— 那是 Rust 那侧没走代理。这正是换 reqwest 之后仍然要在 `core/src/net/proxy.rs`
里自己解析一次的原因。

## 解析顺序

每次请求前解析一次(结果缓存 5 秒),换端口不用重启应用:

1. 环境变量 `HTTPS_PROXY` / `HTTP_PROXY` / `ALL_PROXY`(大小写都认),配了 `NO_PROXY` 就按它绕
2. Windows 注册表 `HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings`
   - `ProxyEnable` = 1 才用
   - `ProxyServer`:`127.0.0.1:7890` 或 `http=…;https=…;socks=…` 两种写法都认
   - `ProxyOverride` 当绕过列表
3. 都没有就直连

只配了 `AutoConfigURL`(PAC 脚本)而没有 `ProxyServer` 时:**不猜**,记一条日志后直连。
PAC 是一段 JS,自己实现只会猜错(脚本、DNS、多级回退),不如承认做不到。

`ProxyEnable = 0` 时这一条请求当然直连,但 `ProxyServer` 里那个地址**不会被丢掉**:
它作为"没启用的代理"留着当第二手,只在直连失败之后才试(见下一节的第三行)。

## 日志里怎么看走了哪条

启动时、以及路由发生变化时,日志里会有一行:

```
PROXY route=http://127.0.0.1:7890 note=系统代理(注册表)
```

- `route=direct` = 直连;`note` 说明为什么(没有代理设置 / 系统代理未启用 / 只有 PAC 等)
- `note=环境变量 HTTPS_PROXY` = 被环境变量接管,注册表那一路不生效
- `note=系统代理(注册表)` = 正常跟上 Windows 的「Internet 选项」

这行是**默认出口**,也就是"某条请求没被单独判定时"走哪条。真正每条请求走哪,由下一节
的按域名选路决定,日志里对应的是 `ROUTE host=… via=…`。

## 按域名自动选路

**同一个应用里,两条路的要求是相反的。** 所以路线不能"全局定一次",只能按 host 收敛。

| 域名 | 直连 | 走代理 |
| --- | --- | --- |
| `cj.lziapi.com`(量子,采集站接口) | 15s,零字节 | **200 / 503 KB / 6s** |
| `super.ffzy-online6.com`(ffzy 的 CDN) | **200** | 403 |
| `v.cdnlz13.com`(分享页) | **200** | 404 |
| 采集站(电影天堂…) | 超时(`os error 10060`) | 正常 |

国内 CDN 按来源 IP 判地区:代理节点在境外,就直接给你 403 / 404 / 451。这不是"地址错了",
是"这条路走不通"。反过来说,采集站直连根本连不上,只有代理那条路能救。两边都真实存在,
所以只能**按域名**决定先走哪条。

### 候选顺序(`net::route::candidates`)

每条请求先算出这个 host 的候选路线,**最多两条**,依次试:

| 情况 | 候选 |
| --- | --- |
| 学过这个 host(`Learned` 命中) | `[学到的]` —— **只有一条,不再试错** |
| 没学过,系统代理**已启用**(环境变量有值 / `ProxyEnable=1`) | `[代理, 直连]` |
| 没学过,系统代理**未**启用,但注册表里仍有 `ProxyServer` | `[直连, 代理(那个地址)]` |
| 完全没有代理配置 | `[直连]` |

第二行:采集站直连超时、必须走代理,所以代理优先。
第三行是给"装了 Clash / v2ray 却没打开系统开关"的用户兜的:直连优先(国内 CDN 要的就是这条路),
**只有直连失败之后**才会去试那个没启用的代理地址,日志里会写清是这一步救回来的。
第四行:没有代理就是没有,不编一条不存在的路出来。

### 什么算"这条路走通了"

- 没有 transport error(没超时、没被拒、代理端口开着),**并且**
- 状态码**不**属于 `http::should_fallback`

| 结果 | 算不算走通 |
| --- | --- |
| 200 / 206 / 3xx | 走通,这就是答案 |
| 403 / 404 / 410 / 451 | 不走通,换下一条 |
| 连不上:超时、连接被拒、代理端口没开 | 不走通,换下一条 |
| 401 / 429 / 5xx | 走通(对方已经明确表态,换条路一模一样) |

第一条走通就返回,并把它**记下来**。

### 记忆与 TTL

走通的那条路线立刻记进 `net::route::Learned`(host → 路线):

- **TTL 30 分钟**(`route::TTL_SECS`):够覆盖一次浏览 / 一集剧,又不至于把换端口、换节点
  之后的旧结论钉太久。
- **容量 256 个 host**(`route::CAPACITY`),超了淘汰**最久没用到**的那条。
- host 统一小写、去掉端口:同一个站换端口还是同一台机器。
- **只在成功后写入**。两条都失败就什么都不记 —— 记了等于把一次"暂时连不上"钉成结论。
- 记着的那条后来不通了(换了节点、代理工具关了),这一条请求会失败,同时**忘掉它**:
  下一次请求重新试错,不会在剩下的 TTL 里一直撞同一堵墙。

记下来省的是**每个分片一次往返**:没有记忆时,ffzy 的每一片都要先撞一次代理的 403 再回退。
分片每秒一片,这一来一回很不划算。

### 两条都不通

返回**最后一条**的错误,串里带上每条路各自的结果(排查时不用猜第二条发生了什么):

```
NETWORK: 请求超时(https://cj.lziapi.com/api.php/provide/vod)
(各条路:proxy:http://127.0.0.1:7890=NETWORK: 连不上(检查代理):… | direct=NETWORK: 请求超时(…))
```

状态码也是一种"结果",所以两条都回 4xx 时串里是 `proxy:…=status:403 | direct=status:404`。

### 日志怎么认

首次判定(不是记忆来的)会记一行:

```
ROUTE host=super.ffzy-online6.com via=direct reason=status:403
ROUTE host=cj.lziapi.com via=proxy reason=ok
```

- `via=direct|proxy` = 最终走通的那条
- `reason=status:NNN` / `reason=transport` = **前一条**候选为什么被换掉;`reason=ok` = 第一条就通了

命中记忆时**不打日志**(分片每秒一片,打出来会把日志淹掉);只有记忆里那条失败时才打:

```
ROUTE host=cj.lziapi.com via=direct (cached) reason=transport
```

两条都不通时:

```
ROUTE host=… FAILED direct=NETWORK: 请求超时(…) | proxy:http://127.0.0.1:7890=status:403
```

反代拿上游时还会多一行,把这条请求和源地址对上(只在"换过路"时出现):

```
PROXY route=direct note=换路 reason=status=403 target=https://super.ffzy-online6.com/…
```

想知道"某条源整体走的哪条路",看上面那行 `ROUTE host=… via=…`;启动时那行
`PROXY route=…` 只是"系统代理现在的默认出口",不再代表每一条请求。

### 边界

- **插件抓取不走选路。** `client_no_redirect()` 那条路仍然是"自己一跳一跳跟",每一跳都要过
  SSRF 检查,插件的跳转语义不能被第二发请求打乱。
- **记忆的 key 只有 host。** 同一个 CDN 的分片、清单、封面共用一条结论 —— 这是故意的:
  它们要走的就是同一条路。
- **没有代理的用户就是没有。** 被墙的源救不了:两条候选都是直连,失败就是失败,错误卡片
  只会给「重试」和「源管理」。**能做的只有换源**,别指望这里再变出第三条路来。
  同理,PAC-only(`AutoConfigURL`)仍然不猜:自己实现 PAC 解释器只会猜错。

## FakeIP 为什么必须放行

Clash / sing-box 的 FakeIP 模式把域名解析到 `198.18.0.0/15`。这块地址属于保留段,常规
SSRF 防护会当内网拒掉 —— 结果是**代理配得越对,请求越全被拦**。

所以 `core/src/net/policy.rs` 明确把这一段列为例外,同时保留其余黑名单(`127.*`、`10.*`、
`192.168.*`、`172.16-31.*`、`169.254.*`、`100.64-127.*`、`::1`、`fe80:`、`fc00:`、`fd00:`)。
另一个坑是 DNS 同时返回 IPv4 与 IPv6:FakeIP 只出现在 IPv4 上,若因为那条被拦的 IPv6
整个拒绝,同样会误伤 —— 只要有一条可用 IPv4,就把不该连的 IPv6 摘掉继续。

## 超时与重试

| 场景 | 连接 | 整体 |
| --- | --- | --- |
| 普通请求(接口 / 分享页 / 清单) | 10s | 20s |
| 媒体流(反代) | 10s | 不设(一部电影可能两小时) |

GET 失败重试一次,间隔 800ms(**同一条路线上**重试);POST 不重试。重试只对"请求本身没成功"
生效,4xx/5xx 是源站的回答,不值得重试 —— 那是换路(见上)该管的事。

**后面还有候选路线时,不在这一条上重试**:换下一条就是重试,不必先在同一条死路上多等
一个超时。所以最坏耗时是"一条路的 20s + 800ms 重试",而不是两条路各自再重试一遍。

前端据此对齐:列表的骨架屏兜底超时是 **22 秒**(`ui/app.js` 的 `SKEL_TIMEOUT_MS`)= 后端一次
20 秒 + 一次 800ms 重试。比这更短会在后端还在试的时候先把界面判死。

## 验证

```
cargo test -p reelbox-core        # net::proxy 覆盖解析链(含"没启用但配着的代理")与 FakeIP,
                                 # net::route 覆盖学过命中 / TTL 过期 / 容量淘汰 / 候选顺序,
                                 # net::http   覆盖 should_fallback、选路决策与错误串
```

手动验证(开着系统代理):打开一次列表,日志里应先是启动那行 `PROXY route=…`,随后是本条
源的 `ROUTE host=… via=… reason=ok|status:NNN`;同一个源再拉一次,`ROUTE` 那行**不再出现**
= 命中记忆。关掉系统代理(5 秒缓存过期后)`PROXY route=…` 变成
`direct note=系统代理未启用`,而 ffzy / `v.cdnlz13.com` 的请求会直接走直连、不再撞 403/404。

没开系统开关但装着代理工具时:`ROUTE host=… via=proxy reason=transport` 说明直连先失败了、
第二手(那个没启用的代理)救回来的。

被墙的源:两条候选都失败,日志里是 `ROUTE host=… FAILED direct=… | proxy:…=…` ——
这时候**只能换源**,应用这边没有第三条路。

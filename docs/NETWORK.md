# 网络出口与系统代理

**应用里没有「设置代理」这个开关。** 出口一律跟着系统走:系统开着代理就走代理,系统没开
就直连。普通用户不需要知道这件事,也不该被问 —— 所以设置页里没有这一栏,连不上时的
错误卡片只给「重试」和「源管理」。

状态:已实现,`cargo test -p reelbox-core` 覆盖解析链、FakeIP 例外,以及代理失败时
回退直连的判定(见「双路兜底」)。

## 为什么"开了系统代理还是连不上"(历史)

应用里有两条完全独立的网络路径:

| 谁在发请求 | 实现 | 跟系统代理 |
| --- | --- | --- |
| 播放器拉分片、页面里的 `<img>` | WebView2(Chromium) | 是,内核自己读系统设置 |
| 源接口、详情、取流、封面、插件里的 `http.get` | Rust + reqwest | **否**,要自己解析 |

WebView2 是 Chromium,系统代理它自己会跟;reqwest 不会。所以代理开着、分片能拉,列表却
超时 —— 那是 Rust 那侧没走代理。这正是换 reqwest 之后仍然要在 `core/src/net/proxy.rs`
里自己解析一次的原因。

## 解析顺序

每次请求前解析一次(结果缓存 5 秒),换端口不用重启应用:

1. 环境变量 `HTTPS_PROXY` / `HTTP_PROXY` / `ALL_PROXY`(大小写都认),配了 `NO_PROXY` 就按它绕
2. Windows 注册表 `HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings`
   - `ProxyEnable` = 1 才用
   - `ProxyServer`:`127.0.0.1:7890` 或 `http=…;https=…;socks=…` 两种写法都认
   - `ProxyOverride` 当绕过列表
3. 都没有就直连

只配了 `AutoConfigURL`(PAC 脚本)而没有 `ProxyServer` 时:**不猜**,记一条日志后直连。
PAC 是一段 JS,自己实现只会猜错(脚本、DNS、多级回退),不如承认做不到。

## 日志里怎么看走了哪条

启动时、以及路由发生变化时,日志里会有一行:

```
PROXY route=http://127.0.0.1:7890 note=系统代理(注册表)
```

- `route=direct` = 直连;`note` 说明为什么(没有代理设置 / 系统代理未启用 / 只有 PAC 等)
- `note=环境变量 HTTPS_PROXY` = 被环境变量接管,注册表那一路不生效
- `note=系统代理(注册表)` = 正常跟上 Windows 的「Internet 选项」

## 双路兜底:代理走不通就直连再来一次

**两个方向都真实存在,所以两条路都得留着。**

| 源 | 直连 | 走代理 |
| --- | --- | --- |
| 采集站(电影天堂、量子…) | 超时(`os error 10060`) | 正常 |
| 国内 CDN(如 `v.cdnlz13.com`) | 正常 | **404** |

实测同一条分享页地址 `https://v.cdnlz13.com/share/0fbdcafcce2cb11f51c99c4d667b1488`:

```
直连     → 200,2430 字节
走 7890  → 404,881 字节
```

国内 CDN 按来源 IP 判地区,代理节点在境外就直接给你 404(有的是 403 / 451),
这不是"地址错了",是"这条路走不通"。所以只看"系统开着代理"就一路走代理是错的 ——
上一版修好了采集站(直连超时),却把 CDN 这类源一起打死了。

于是每次 GET 都是:先按系统代理走;如果这条路的回答是"此路不通",**同一条请求**
(同样的地址、请求头、Range)再直连发一次,用后者的结果。

### 触发条件

| 第一次的结果 | 是否换直连 |
| --- | --- |
| 403 / 404 / 410 / 451 | 换(见 `http::should_fallback`) |
| 连不上:超时、连接被拒、代理端口没开 | 换 |
| 200 / 206 / 3xx | 不换,这就是答案 |
| 401 / 429 / 5xx | 不换 —— 对方已经明确表态,换条路一模一样 |

两条边界:

- **第一次必须真的走了代理**。本来就在直连时没有第二手,直接返回结果
  (决策是纯函数 `http::plan(第一次的结果, 是否走代理)`,单测覆盖)。
- **插件抓取不走兜底**。`client_no_redirect()` 那条路仍然是"自己一跳一跳跟",
  每一跳都要过 SSRF 检查,插件的跳转语义不能被第二发请求打乱。

直连也失败时,错误串里两次都写着(`…(代理那条路:…)`),排查时不会只看到
"连不上"而不知道第一跳发生了什么。

### 日志里怎么认

```
HTTP fallback direct reason=status:404 url=https://v.cdnlz13.com/share/…
HTTP fallback direct reason=transport url=https://… err=NETWORK: 连不上(检查代理):…
```

- `reason=status:NNN` = 代理那边的回答是"此路不通",直连救回来的
- `reason=transport` = 代理那条路压根没连上,直连救回来的

反代拿上游时还会多一行,把这条请求和源地址对上:

```
PROXY route=direct note=代理失败回退 reason=status:404 target=https://…
```

**这两行没出现 = 第一跳(系统代理)就成功了**,一次请求搞定。想知道"这条源整体走的
哪条路",还是看启动时那行 `PROXY route=…`;`HTTP fallback direct` 那行是**单条请求**级别的,
反代那行 `PROXY route=direct note=代理失败回退` 只在该条上游请求被救回来时出现。

### 代价

兜底是**每条请求现判**,不记忆。所以一个被 geo 挡的 CDN,它的每一个分片都会
先撞一次代理的 404 再直连 —— 多一次请求、多一点延迟,但不会播不出来。
换来的是"代理配得对还是错,都能播",这比省一次请求重要。

## FakeIP 为什么必须放行

Clash / sing-box 的 FakeIP 模式把域名解析到 `198.18.0.0/15`。这块地址属于保留段,常规
SSRF 防护会当内网拒掉 —— 结果是**代理配得越对,请求越全被拦**。

所以 `core/src/net/policy.rs` 明确把这一段列为例外,同时保留其余黑名单(`127.*`、`10.*`、
`192.168.*`、`172.16-31.*`、`169.254.*`、`100.64-127.*`、`::1`、`fe80:`、`fc00:`、`fd00:`)。
另一个坑是 DNS 同时返回 IPv4 与 IPv6:FakeIP 只出现在 IPv4 上,若因为那条被拦的 IPv6
整个拒绝,同样会误伤 —— 只要有一条可用 IPv4,就把不该连的 IPv6 摘掉继续。

## 超时与重试

| 场景 | 连接 | 整体 |
| --- | --- | --- |
| 普通请求(接口 / 分享页 / 清单) | 10s | 20s |
| 媒体流(反代) | 10s | 不设(一部电影可能两小时) |

GET 失败重试一次,间隔 800ms;POST 不重试。重试只对"请求本身没成功"生效,
4xx/5xx 是源站的回答,不值得重试 —— 那是兜底(见上)该管的事。

## 验证

```
cargo test -p reelbox-core        # 其中 net::proxy / net::policy 覆盖解析链与 FakeIP,
                                 # net::http 覆盖 should_fallback 与兜底决策 plan
```

手动验证:开着系统代理打开列表,日志里的 `PROXY route=…` 应该指向代理地址;关掉系统代理
(5 秒缓存过期后)同一行会变成 `route=direct note=系统代理未启用`。

兜底的手动验证(一条命令,两个方向都能看):把 `HTTPS_PROXY` 指向一个不存在的端口,
再用 `curl` 直接对比。代理那条路连不上时,日志里应出现
`HTTP fallback direct reason=transport`,而请求照样成功。

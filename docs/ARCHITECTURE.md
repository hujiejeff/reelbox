# 架构：内核 / 适配器 / 解析器

状态:2026-11-21 定稿,分批实施中。本文记录**为什么这样分层**、**迁移顺序**,以及每一步的验收口径。
相关文档:[SOURCES.md](SOURCES.md)(源是什么)、[PLUGIN.md](PLUGIN.md)(插件契约)、[ENGINE-PLUGINS.md](ENGINE-PLUGINS.md)(iplayr 这类配置引擎)、[PARSERS.md](PARSERS.md)(解析器)。

## 1. 三层,别再加第四层

```
        ┌──────────── 内核(Rust)────────────┐
        │ 网络出口 · 播放反代 · 沙箱宿主 · UI │
        └───────────────┬───────────────────┘
                        │ 只认三个方法
                   list / detail / play
                        │
        ┌───────────────┴───────────────────┐
        │  适配器(JS):把某种格式翻译成这三个   │
        │  vod · iplayr · webox · reelbox    │
        └───────────────┬───────────────────┘
                        │ 源交出的可能是"一张网页"
        ┌───────────────┴───────────────────┐
        │  解析器(JS):网页 → 播放地址         │
        └───────────────────────────────────┘
```

- **内核**:凡是"所有源都需要、而且必须一致"的东西——HTTP 出口、代理选路、超时重试、播放反代、沙箱、界面。**站点相关的逻辑一行都不许进来。**
- **适配器**:把一种"源格式"翻译成 `list/detail/play`。数据来自 API、HTML、还是本地文件,内核不关心。
- **解析器**:只在适配器交出的是一张网页、且内置正则抽不出地址时才被调用;它不知道"列表""剧集"是什么。

多一层的诱惑一直存在(比如"传输层""映射层")。**不加**。表达不了的格式就写适配器,而不是再造一层抽象。

## 2. 源 = 适配器 + 配置

`%APPDATA%\reelbox\sources.json` 里一条源:

```json
{
  "id": "…",
  "name": "独播库",
  "adapter": "iplayr",
  "config": "https://…/iplayr/dbk.json",
  "probe": { "at": "2026-11-21T07:30:00Z", "ok": true, "items": 48, "sample": "极限逃生" }
}
```

| 字段 | 含义 | 谁写 |
| --- | --- | --- |
| `adapter` | 用哪个适配器解析 | 导入时探测决定,**运行时不改** |
| `config` | 解析哪一个站(接口地址 / 配置文件 / 插件路径) | 用户提供 |
| `probe` | 当初判定成功的证据 | 探测时写入 |

4K 那种单站插件的 `config` 是**插件文件路径**,规则全在文件里;CMS 的 `config` 是接口地址;iplayr 的是规则文件地址。同一个字段,三种用法——因为适配器自己知道该怎么解释它。

### 为什么判定只做一次

如果每次加载都重新猜格式,会出现"昨天能看,今天变成另一个适配器"的鬼故事,而且报错无法定位。**判定发生在导入,结果落盘**,之后一切按 `adapter` 走。判定错了可以重新探测(设置里给一个入口),但不会自己变。

## 3. 导入即探测

```
用户粘地址 / 选文件
      ↓
① 静态特征(不发网络)
      ↓ 缩小到 1~3 个候选
② 依次试跑 list(page=1),每个限时 8 秒
      ↓
③ 第一个出条目的 → 定案,写 adapter + probe
```

### 静态特征表

| 看到什么 | 候选 |
| --- | --- |
| 源码含 `reelbox.define(` | `reelbox` |
| 源码含 `reelbox.parser(` | 不是源(解析器),单独处理 |
| 源码含 `WeBox.define(` | `webox` |
| 源码是 `export default function (hg)` | `hghub`(未实现) |
| JSON 同时有 `category` 与 `vod_node` | `iplayr` |
| 地址含 `api.php/provide/vod`、`ac=list` | `vod` |
| 地址以 `.xml` 结尾 / 含 `ac=xml` | `vod`(XML 变体) |

### 试跑失败要分三种,不能一刀切

| 结果 | 判定 | 用户看到 |
| --- | --- | --- |
| 出 ≥1 条 | 成功 | 直接建源 |
| `parse` / `unsupported` | 格式不对 | 「这个地址不是能识别的源格式」+ 原始返回前 100 字 |
| `network` / 超时 | **判不了** | 「网络没通,源已保存,可稍后重试」——不判死 |

第二、三行必须分开:把网络问题说成"格式不支持",用户会去改一个本来没错的地址。

### 只试 list

列表能出来,说明适配器对了。`detail/play` 的失败往往是单集问题(B 站改版、某集下架),不该否定整个源。

## 4. 适配器契约(JS)

```js
reelbox.adapter({
  id: "iplayr",
  name: "iplayr 配置",
  version: "1",
  accepts: { kind: "json", has: ["category", "vod_node"] },  // 判型用
  async probe(ctx, { config }) { … },                        // 可选:更细的探测
  async list(ctx, { config, page, filters }) { … },          // 必需
  async detail(ctx, { config, id }) { … },                   // 必需
  async play(ctx, { config, id }) { … },                     // 必需
});
```

- 所有网络请求走 `ctx.http`(内核出口),适配器不碰 socket。
- 错误只能用四类码:`network` / `parse` / `auth` / `unsupported`。
- 适配器**不持有全局状态**;同一份 config 的缓存可以放在 `ctx.cache`(内核提供,按 config 键)。

### 性能实测(决定 P3 能不能做的依据)

沙箱内对 `cj.lziapi.com` 的 165 KB XML:

| 步骤 | 耗时 |
| --- | --- |
| 网络取回 | 1031 ms |
| DOMParser 解析 | **6 ms** |
| 抽取 20 条 | 0 ms |
| XPath 取 20 个节点 | 8 ms |

结论:解析不是瓶颈,网络才是。所以 vod 可以放心放在沙箱里;只有当响应体到几 MB 级别时才需要考虑内核原语。

### 一致性验证(P3 验收)

`非凡资源`(JSON)、`量子资源`(XML)、`电影天堂`(JSON)三个源,JS 与 Rust 实现的输出:

- 列表:条数、`next`、前 3 条 `{id,title,kind,poster,subtitle}` 完全一致
- 详情:`title`、线路数、每组集数、前 3 集 `{id,name}` 完全一致
- 分类:数量一致
- 播放:地址、`page` 标记、`Referer` 一致

采集站返回顺序会轮换,比对必须按 `id` 对齐,不能按数组下标。

## 5. 迁移计划

| 阶段 | 内容 | 风险 | 验收 |
| --- | --- | --- | --- |
| **P1** | `adapter` + `probe` 字段;老数据按 `type` 自动迁移;运行时按 `adapter` 分发 | 低(纯重构) | 113 条测试不掉,现有 9 个源行为不变 |
| **P2** | 导入探测:静态特征 + 试跑 list;三态失败 | 中(涉及网络) | 粘 `…/iplayr/dbk.json` → 自动建源,不碰插件 |
| **P3** | `vod` 从 Rust 迁到 JS 适配器 | 中(性能) | 同一批 CMS 源输出逐字段一致;500 KB XML 解析 < 800ms |
| **P4** | `webox` 抽成独立适配器(现在藏在宿主里) | 低 | 老插件行为不变 |
| **P5** | `hghub` / `tvbox` 适配器 | 中 | 各跑通一个真实样本 |

**P3 的前置**:先量。拿量子那份 503 KB XML,在沙箱里 `DOMParser` + 遍历出 20 条,记录耗时;超过 800ms 就把"解析大文档"做成内核原语(`ctx.xml.load` 在 Rust 侧解析),而不是硬扛。

**每阶段都可独立上线**,不做"一次性大重构"。

## 6. 决策记录

**为什么要 JS 适配器,而不是全 Rust**
维护者写了"这个 App 我不可能一直维护"。Rust 适配器意味着站点一改就得编译发版;JS 适配器改一个文件、导入即生效,别人也能替我们修。

**为什么不把 iplayr 的 JSON 结构写进 Rust**
一旦写成结构体,字段变化就要发版。JSON 只在适配器里被理解为"一堆 XPath 字符串",内核完全不知道它长什么样。

**为什么不做 DSL / 万能映射**
配置只能表达"从哪儿取",不能表达"怎么算"。越线就会长成一门半吊子编程语言:难写、难调、没人用。需要计算(签名、解密、wasm)的,一律写适配器。

**为什么解析器是旁路而不是适配器的一种**
它没有列表、没有详情,输入是一张网页,输出是一个地址。放进适配器会污染 `list/detail` 的语义。

## 7. 非目标

- 执行外部生态的二进制插件(TVBox `spider.jar`、Python spider)——没有 JVM/解释器,不做。
- 需要浏览器渲染/过 Cloudflare 的站点——除非将来加 `ctx.browser` 能力,否则明确报 `unsupported`。
- 把匹配规则做成可视化编辑器——配置是文本,够用。

## 8. 已知代价

- **配置会腐烂**:站点改版 → XPath 失效。这是配置驱动模式的固有成本,缓解手段是"报错指向具体哪一步"和"改配置不发版"。
- **JS 适配器慢于 Rust**:同一份 500 KB XML,Rust 几十毫秒,沙箱里可能几百毫秒。列表本身要等网络 4–6 秒,所以通常无感;大文档场景走内核原语。
- **探测要发网络**:导入变慢(多一次 8 秒上限的请求)。可接受——总比导进来才发现不能用好。
